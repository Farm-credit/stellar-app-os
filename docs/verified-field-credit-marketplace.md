# Verified field-data carbon credits (Drips #1650)

## Data eligibility

The existing `research_samples` schema stores measured CO2 in kilograms but previously had no review state. Migration `030_verified_field_carbon_credit_issuance.sql` adds a `pending`-by-default `verification_status`, plus reviewer identity and timestamp. Rows become eligible only after the trusted research review workflow explicitly records `verification_status = 'verified'`, a non-empty `verified_by`, and `verified_at`. Rejected/pending rows, rows without measurements, and satellite-derived/modelled rows are excluded. The associated tree must also be marked `verified`, have an active record, and be attributed to the requested sponsor wallet.

Credits are derived from the positive difference between two verified `co2_kg` readings for the same tree and research plot. The first verified reading is the baseline; after a successful issuance, the newest issued sample becomes the next baseline. Thus a single reading, a zero/negative delta, or a repeat of an already reserved sample does not issue credits. Kilograms are converted to grams only at the final calculation step. The canonical evidence hash binds sponsor, tree, plot, sample identifiers, measurement values and methods, reviewer identities, review timestamps, and the issued delta. Database uniqueness plus the Soroban write-once digest prevent duplicate issuance.

## Issuance API and authorization

`GET /api/field-credits?sponsorWallet=<G...>` previews sample-derived eligibility. `POST /api/field-credits` accepts `{ "sponsorWallet": "G...", "treeId": 123, "network": "testnet" }` to reserve and issue the newest eligible delta. Both endpoints require `Authorization: Bearer <FIELD_CREDIT_ISSUER_TOKEN>`. Provision a fresh random token of at least 32 characters in the server environment; it is privileged and must never be exposed to browser code. Issuance also requires `DATABASE_URL`, `NEXT_PUBLIC_CONTRACT_CARBON_CREDITS`, `STELLAR_FEE_PAYER_SECRET`, and a correctly configured Soroban contract/network. The fee-payer must be the contract's configured admin. The API only confirms issuance after Soroban reports transaction success.

A database issuance row is reserved before the on-chain call. If transaction submission or confirmation times out, the row remains `pending` and the endpoint refuses an automatic retry. This is intentional: Soroban may have accepted a transaction even if the client did not observe finality. Reconcile the digest against the contract's `get_field_credit` entry and the network transaction history before changing that row or retrying. Do not clear pending reservations as routine cleanup.

## Marketplace flow

The `/marketplace` page includes a separate verified-field section. It scans at most the latest 25 contract retail-lot IDs and includes only active lots for which `get_field_retail_lot_digest` returns a field evidence digest; legacy modeled retail lots are not presented as verified field credits. The public listing response is briefly cached to bound RPC load. The evidence lookup endpoint (`GET /api/field-credits/issuance?digest=<64-char-hex>`) exposes a specific public on-chain issuance record and remaining unlisted grams. The seller must possess the digest from the trusted issuance receipt and connect the sponsor wallet recorded on-chain. The seller chooses a whole-ton quantity and an explicit payment-token base-unit price, then signs `open_field_credit_lot` in their wallet. Buyers sign `buy_retail_portion`; payment goes to the seller in the configured retail token and the contract credits the buyer's carbon balance. The listing retains its digest link, and contract retail events provide the transfer trail.

Marketplace read routes use the configured Soroban contract and the server-side fee-payer account for simulation. Configure `NEXT_PUBLIC_CONTRACT_CARBON_CREDITS`, `NEXT_PUBLIC_STELLAR_NETWORK`, and `STELLAR_FEE_PAYER_SECRET`; do not expose the fee-payer secret. Wallet-signed transactions are submitted directly by the browser to Soroban RPC. The UI can read and prepare these methods only after the contract deployment includes the field-credit entry points.

## Deployment, review, and caveats

These contract changes are source changes only: deploy/upgrade the Soroban WASM, initialize/configure the instance, set its admin, and configure the retail payment token before a production marketplace can issue or trade field credits. Existing deployed instances do not acquire new entry points from an application deploy alone. The app's current `NEXT_PUBLIC_CONTRACT_CARBON_CREDITS` setting is a single configured ID; use separate deployment environments for testnet and mainnet. Existing sample rows stay pending until explicitly reviewed; no historical/demo measurement is silently treated as verified.

The application does not claim third-party registry certification or independent scientific verification. `verified_by` and `verified_at` are provenance supplied by the upstream reviewer; maintainers must ensure the data-entry/review workflow that writes those fields is itself access-controlled and auditable. Token price is expressed in the configured token's base units; confirm token decimals and deployment configuration before trading.
