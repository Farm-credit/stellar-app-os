## Summary

Implements the storage-footprint audit and optimization requested in issue #1817.

Soroban has three storage classes, but the shared contract suite defaulted to `env.storage().persistent()` even for short-lived state. Persistent entries stay in the live ledger (and in every footprint that touches them) for their whole lifetime, while instance storage shares a single auto-bumped TTL and temporary storage entries are reclaimed when their TTL expires. This PR adds one shared storage-class policy for the whole `contracts/` tree and migrates the two places that were using the wrong class.

### What changed

- **`contracts/contract-utils/src/storage.rs` (new)** — the single source of truth for storage-class selection:
  - `StorageClass` (`Instance` / `Temporary` / `Persistent`) and `DataLifetime` (`Config`, `Counter`, `HotAccumulator`, `Cache`, `ReplayGuard`, `AuditRecord`, `Balance`, `Ownership`) with `DataLifetime::storage_class()` encoding the decision matrix from the audit;
  - generic `get` / `set` / `has` / `remove` helpers over `soroban_sdk::Env` for all three classes, with automatic per-entry TTL extension for temporary and persistent values;
  - `mark_replay_guard` / `replay_guard_active` convenience API with `REPLAY_GUARD_TTL_LEDGERS = 518_400` (~30 days);
  - 6 unit tests covering the classification policy, round-trips in every class, and TTL expiry of a replay guard.
- **`contracts/bonus-pool/`** — `DataKey::ProcessedSale(sale_id)` was a one-shot replay marker kept in persistent storage forever. It is now a temporary replay guard via the shared helpers, so stale sale markers leave the live ledger instead of growing the footprint with every historical sale. Added two tests: duplicate `sale_id` is still rejected inside the TTL, and the same `sale_id` can be routed again after the TTL (proving reclamation).
- **`contracts/zk-location-verifier/`** — all four inline temporary-storage cache accesses now go through `contract_utils::storage`, so class and TTL policy has a single source of truth. Behaviour and the configurable `PRFTTL` are unchanged; the existing 43 unit + 3 integration tests still pass.
- **`contracts/contract-utils/src/auth.rs`** — fixed two pre-existing tests that panicked with `no contract running` by executing the auth helpers through a registered test contract (`env.as_contract`). Required for a green `cargo test -p contract-utils`.
- **`docs/contracts/storage-footprint-optimization.md` (new)** — audit report: storage-class semantics, decision matrix, audit findings across all 49 contract crates, normative rules (in particular: replay guards that may be needed indefinitely must stay persistent, caches must be recomputable), and verification steps.

### Compatibility / zero regression

No public contract function signature, error code, event or stored value layout changed. Config/counter state that was already in instance storage, and per-entity records that legitimately use persistent storage, were left untouched. The only behavioural change is that a `bonus-pool` sale marker expires after ~30 days, which is safe because `sale_id` is a globally unique monotonic marketplace id and the guard only needs to cover the settlement window.
